# cohomology-tables

Cohomology rings and **cup product multiplication tables** for spaces with a
simplicial model, built on the experimental hypercomplex machinery in
[OSCAR](https://www.oscar-system.org/).

Give it a simplicial complex and a coefficient ring; it computes `H^*(K; R)`,
puts each graded piece in canonical form, names a basis, prints the full cup
product table, and identifies the ring when it is generated by a single class.
It also computes **homology** `H_*(K; R)` over `ZZ`, `QQ` and `GF(p)`.

It ships with a catalogue of **203 spaces**, one simplicial model per
topological type, drawn from SageMath's example catalogue, Frank Lutz's Manifold
Page and the literature, and with computed records for all of them: cup product
rings, and homology over six coefficient rings. **No triangulations are stored
in this repository** — models are built by Sage or downloaded on first use and
cached outside the repo.

```julia
julia> X = simplicial_cohomology_ring("K3_16", lutz("K3_16"), GF(7));
julia> print_report(X)      # the 22 x 22 intersection form of K3 mod 7
```

```
========================================================================
RP^4   coefficients in F_2
========================================================================
simplicial model: dim = 4, f-vector = [16, 120, 330, 375, 150]

cohomology groups
  H^0 = F_2                    basis: 1
  H^1 = F_2                    basis: x1
  H^2 = F_2                    basis: x2
  H^3 = F_2                    basis: x3
  H^4 = F_2                    basis: x4

cup product table  (row * column)
       |    1   x1   x2   x3   x4
  -------------------------------
      1|    1   x1   x2   x3   x4
     x1|   x1   x2   x3   x4    0
     x2|   x2   x3   x4    0    0
     x3|   x3   x4    0    0    0
     x4|   x4    0    0    0    0

ring structure: F_2[x1]/(x1^5),  |x1| = 1
checks: unit law and graded commutativity hold
```

## Requirements

* **Julia 1.10+ and OSCAR 1.8+** (developed against Julia 1.12 / OSCAR 1.8.2).
  The cohomology-ring code lives in OSCAR's
  `experimental/DoubleAndHyperComplexes`, so an older OSCAR will not have it.
* **SageMath is optional.** 32 of the 203 catalogue entries are built by
  invoking a Sage constructor; without `sage` on the `PATH` those raise a clear
  error naming the missing binary, and the other 171 (162 from the Manifold
  Page, 8 built here, 1 from arXiv) work normally. `scripts/regenerate_sage.jl`
  needs it; `scripts/fetch_sources.jl` and the offline test suite do not. Set
  the `SAGE` environment variable if it lives somewhere unusual, and
  `sage_available()` reports what the package can see.
* **A network connection**, the first time you ask for a Manifold Page or arXiv
  model. Files are cached in `cache_dir()` — a scratchspace in your Julia depot,
  never inside the repo — so it happens once. Override with
  `COHOMOLOGY_TABLES_CACHE`; `clear_cache()` empties it.

```bash
git clone https://github.com/wgabrielong/cohomology-tables
cd cohomology-tables
julia scripts/run_tables.jl --list      # the catalogue; no network, no Sage
julia test/runtests.jl                  # offline checks; no network, no Sage
julia test/runtests.jl --online         # + Sage and Manifold Page checks
```

The 1409 records under `records/` are committed — 227 cup product rings and 1182
homology records — so every computed result can be read with neither Sage nor a
network connection. Both are only needed to rebuild a complex and recompute.

If OSCAR is already in your default environment, every command works as written.
Otherwise run `julia --project=. -e 'using Pkg; Pkg.instantiate()'` once and add
`--project=.` to each command.

## Computing a space

Load the module, then pick a model and a coefficient ring:

```julia
julia> include("src/CohomologyTables.jl"); using .CohomologyTables
julia> using Oscar
```

**From the catalogue** — `catalogue_space(name)` builds the model for a catalogue entry:

```julia
julia> X = simplicial_cohomology_ring("K3", catalogue_space("K3"), GF(7));
julia> print_report(X)

julia> print_report(simplicial_cohomology_ring("L(3,1)", catalogue_space("L(3,1)"), ZZ))
julia> print_report(simplicial_cohomology_ring("RP^4", catalogue_space("RP^4"), GF(2)))
```

**Straight from a source**, bypassing the catalogue — useful when you want a
particular triangulation rather than a particular space:

```julia
julia> X = simplicial_cohomology_ring("K3_16", lutz("K3_16"), GF(7));
julia> print_report(X)                       # the 22 x 22 intersection form of K3 mod 7

julia> lutz("RP5_24")                        # Manifold Page, one complex per file
julia> lutz("flat_3manifolds", "T^3")        # one complex out of a file of many
julia> lutz_labels("spherical_3manifolds")   # what is in such a file
julia> lutz_header("K3_16")                  # the file's own f-vector, homology, references

julia> sage("Torus()")                       # anything in Sage's catalogue
julia> sage("SurfaceOfGenus(4)")
julia> sage("MooreSpace(5)")
```

**From your own complex** — see [below](#using-your-own-simplicial-complex).

The first argument to `simplicial_cohomology_ring` is only a label for the
printout. The third is any OSCAR ring: `ZZ`, `QQ`, `GF(p)`, `GF(p, n)`.

### Batch runs

```bash
julia scripts/run_tables.jl --list                     # print the catalogue
julia scripts/run_tables.jl --list --provenance Sage   # ... one source only
julia scripts/run_tables.jl --only K3 --only "L(3,1)"  # named spaces
julia scripts/run_tables.jl --provenance Lutz/3-manifolds --coeffs GF7
julia scripts/run_tables.jl --time-limit 120 --out tables.txt
julia scripts/run_tables.jl                            # all 197 computable spaces
julia scripts/run_tables.jl --all                      # ... plus the six that don't finish
```

### Working with the result

```julia
julia> X = simplicial_cohomology_ring("T^2", catalogue_space("T^2"), QQ);

julia> top_degree(X)                    # 2
julia> graded_basis(X, 1).labels        # ["x1_1", "x1_2"]
julia> graded_basis(X, 1).orders        # [0, 0]  -- 0 means a free summand

julia> cup(X, (1, 1), (1, 2))           # x1_1 ∪ x1_2, as coordinates in H^2
1-element Vector{Any}:
 1

julia> cup(X, (1, 2), (1, 1))           # x1_2 ∪ x1_1 = -(x1_1 ∪ x1_2)
1-element Vector{Any}:
 -1

julia> cup_power(X, (1, 1), 2)          # (x1_1)^2 = 0
1-element Vector{Any}:
 0

julia> identify_ring(X)                 # nothing -- needs two generators
julia> check_ring(X)                    # String[] -- the laws hold
```

Classes are addressed as `(degree, index)` pairs, and every product comes back
as a coordinate vector in the canonical basis of the target degree.

### Choosing coefficients

This matters more than it might seem. `RP^n` over `ZZ` is almost all torsion and
its table looks nearly empty; over `GF(2)` it is `F_2[x]/(x^(n+1))`. Rule of
thumb: `GF(2)` for real projective spaces and anything with 2-torsion, `ZZ` or
`QQ` for spheres and complex projective spaces, `GF(p)` to see `p`-torsion. Each
catalogue entry carries a suggested `coeffs` list. Over a field coordinates are
unique; over `ZZ` they are canonical modulo the order of each summand.

## Homology

`simplicial_homology(name, K, R)` computes `H_*(K; R)` over `ZZ`, `QQ` or
`GF(p)`, in the same canonical invariant-factor form as the cohomology side.

```julia
julia> H = simplicial_homology("RP^4", catalogue_space("RP^4"), ZZ);
julia> print_homology(H)
```

```
RP^4   homology with coefficients in Z
========================================================================
simplicial model: dim = 4, f-vector = [16, 120, 330, 375, 150]

homology groups
  H_0 = Z                      basis: a0
  H_1 = Z/2                    basis: a1
  H_2 = 0
  H_3 = Z/2                    basis: a3
  H_4 = 0
ranks: [1, 0, 0, 0, 0]   Euler characteristic: 1
checks: Euler characteristic and the integral oracle agree
```

This is genuinely different information from the cup product ring, not a
restatement of it. Compare the same space's cohomology, also published here:

```
H_*  = Z, Z/2, 0, Z/2, 0     torsion in odd degrees
H^*  = Z, 0, Z/2, 0, Z/2     torsion in even degrees
```

— the universal-coefficients degree shift.

```julia
julia> homology_group(H, 1)                  # the canonical form of H_1
julia> homology_ranks(H)                     # Betti numbers, degree by degree
julia> free_rank(homology_group(H, 1))       # 0
julia> torsion_orders(homology_group(H, 1))  # [2]
julia> check_homology(H)                     # String[] -- the identities hold
julia> integral_homology_symbols(K)          # H_*(K;Z) from Oscar/Polymake
```

### Why this exists, and how it is computed

**`Oscar.homology(K, i)` takes no coefficient ring** — it is Polymake, and
integral only. Over `QQ` and `GF(p)` there is nothing upstream to ask, which is
what this adds. The two regimes are handled differently because their costs are
completely different:

| coefficients | method | cost |
|---|---|---|
| `QQ`, `GF(p)` | ranks of the boundary matrices of `src/chain_complex.jl`: `dim H_d = n_d − rank ∂_d − rank ∂_(d+1)` | linear algebra; `RP^5` ~7s, `CP^3` ~10s |
| `ZZ` | delegated to `Oscar.homology(K, d)` | Polymake's tuned routine; effectively instant |

`ZZ` delegates deliberately. Torsion needs Smith normal form, and integral SNF
suffers the usual coefficient explosion — `snf` of `RP^5`'s third boundary
matrix (2277 × 1174) did not finish in four minutes here, while Polymake
returns immediately. Recomputing it badly would help nobody.

One consequence worth stating plainly: **over `ZZ` the agreement with
`Oscar.homology` is definitional, not an independent check.** It still catches
packing mistakes, and `scripts/verify_homology.jl --deep` re-derives integral
homology independently (through the subquotient and its Smith form) for
complexes small enough to afford it. Over a field the check against `H^*` *is*
independent, since the cup product side is built from a cochain complex through
OSCAR's `DGAlgCohRing`.

### Verifying

```bash
julia scripts/verify_homology.jl             # cheap pass
julia scripts/verify_homology.jl --cross     # + cross-check against H^*
julia scripts/verify_homology.jl --deep      # + independent integral homology
```

See [Correctness](#correctness) for what each check compares and what the whole
corpus currently reports.

### Cycle representatives are deliberately not stored

`cycle_representative(H, d, j)` exists and works, but **no record ever contains
one**, under any flag. For a closed orientable `n`-manifold the fundamental
class is the signed sum of every `n`-simplex, and in top degree that
representative is unique — so it *is* the facet list. Measured: `S^2` 4 of 4
facets, `T^2` 14/14, `RP^3` 40/40, `CP^2` 36/36. Emitting it would redistribute
the input this repository does not ship. Cohomology is safe by the dual accident
(its cocycle supports are small). See [docs/PROVENANCE.md](docs/PROVENANCE.md).

## Using your own simplicial complex

Anything that produces an OSCAR `SimplicialComplex` works. Give the **maximal
faces** — subfaces are implied.

```julia
julia> K = simplicial_complex([[1,2,3], [2,3,4], [1,3,4], [1,2,4]])   # ∂Δ³ ≅ S²
julia> print_report(simplicial_cohomology_ring("my sphere", K, QQ))
```

From a file of your own, in either format the sources use:

```julia
julia> facets = parse_gap_blocks(read("my_space.txt", String))   # `facets:=[[1,2,3], ...];`
julia> K = simplicial_complex(last(only(facets)))

julia> K = simplicial_complex(relabel_facets([[0,1,2], [1,2,3]]))  # any labels; relabels to 1:n
```

`relabel_facets` renumbers vertices to `1:n` order-preservingly. Worth using:
the Alexander–Whitney cup product is defined relative to a total order on the
vertices, and OSCAR wants `1:n`.

From an OSCAR or Polymake construction:

```julia
julia> K = Oscar.torus()
julia> K = SimplicialComplex(Oscar.Polymake.topaz.poincare_sphere())
julia> K = SimplicialComplex(Oscar.Polymake.topaz.sphere(4))
```

Or from the constructors here: `point_space()`, `sphere(n)`,
`kuehnel_real_projective_space(n)`.

### Adding it to the catalogue

Append a `SpaceEntry` in the relevant section of [`src/spaces.jl`](src/spaces.jl):

```julia
push!(E, SpaceEntry("my space",                 # catalogue key, must be unique
                    "what it is topologically", # shown in --list
                    "Sage",                     # a label from provenances()
                    sage_recipe("Torus()");     # or lutz_recipe(file[, label]),
                                                # builtin_recipe("sphere(3)"),
                                                # arxiv_recipe("1012.3235")
                    coeffs = Any[ZZ, GF(2)],
                    note = "size, caveats, other models of the same type"))
```

An entry stores a `Recipe`, not a closure: a machine-readable instruction that
`build(entry)` executes and that the generated records quote verbatim, so a
record's stated provenance and the complex actually computed from cannot drift
apart. Nothing is fetched until someone asks for that entry, and `catalogue()`
checks that names stay unique.

### What deduplication removed

The sources hold many models of the same space, and the catalogue keeps one of
each. They all remain reachable directly — the entry's `note` says how. For
example `S^3` stands for Sage's `BarnetteSphere()` and `BrucknerGrunbaumSphere()`
and Lutz's `600_cell`, `trefoil`, `nc_sphere`, `non_4_2_colorable` and the
`_bsd` barycentric subdivisions; `point` stands for every contractible complex
in either source, including the dunce hat, Rudin's and Ziegler's balls, Bing's
house and the `BH_k` family; and `S^5` stands for Lutz's `non_PL_5_sphere`,
which is a genuinely non-PL triangulation of the same topological space.

The catalogue was audited by computing integral homology for every entry and
examining each collision. Most collisions are *not* duplicates — distinct
3-manifolds routinely share homology, and telling `CP^2#CP^2` from `S^2xS^2` is
exactly what a cup product table is for. Five were genuine and were merged:
`sage("FareyMap(5)")` is `S^2`, `sage("FareyMap(7)")` is `Sigma_3`,
`sage("MooreSpace(2)")` is `RP^2`, `lutz("d2n12g6")` is `Sigma_6`, and
`lutz("Hom_C5_K4")` is `RP^3` — its own file header states
`Hom(C_5,K_4) = RP^3`.

Lens spaces: the 3-dimensional ones are present from Lutz's spherical catalogue
(`L(3,1)` … `L(10,3)`). SageMath has no lens space constructor, so none can be
had from that source, and higher-dimensional lens spaces are not in the
catalogue.

## Generated records

`records/` holds one JSON record per (space, coefficient ring): the rebuild
recipe, a SHA-256 over the canonicalised facets, every graded piece with a
cocycle representative for each basis class, the structure constants of the cup
product, the ring presentation, and the vertex-ordering convention the
representatives are expressed in.

**A record contains no facet list.** It does name the individual faces in the
support of each chosen cocycle representative — a small subset of the complex's
faces, in dimensions where cohomology is non-zero, from which the complex cannot
be reconstructed. Nothing else about the input is stored beyond its f-vector and
hash.

There are two record families, distinguished by a token in the filename:
`<slug>_<digest>.<coeff>.json` holds a cup product ring, and
`<slug>_<digest>.homology.<coeff>.json` holds homology. Homology records are
generated over a fixed grid — `ZZ`, `QQ`, `GF(2)`, `GF(3)`, `GF(5)`, `GF(7)` —
and carry groups, invariant factors, Betti numbers and torsion, with **no
representatives** and no `vertex_order_convention` (homology does not depend on
the vertex order). As shipped that is 227 ring records and 1182 homology
records, about 12 MB.

```bash
julia scripts/export_records.jl                  # ring records + MANIFEST.tsv
julia scripts/export_homology.jl                 # homology records
julia scripts/export_records.jl --only K3 --coeffs GF7
julia scripts/fetch_sources.jl                   # re-fetch Lutz sources, verify hashes
julia scripts/regenerate_sage.jl                 # rebuild Sage models, verify hashes
```

One caveat the scripts surface: Sage's `SurfaceOfGenus` returns a differently
labelled complex on each process, so the nine `Sigma_*`/`N_*` surface records
cannot be verified by hash. They are marked `reproducible_labelling: false` and
checked against f-vector and homology instead — invariants under relabelling —
and still fail if those differ. The ring is unaffected; only the cocycle
representatives are tied to a labelling.

`MANIFEST.tsv` also carries `f_vector` and `integral_homology` columns. Those
are invariants of the space rather than of a labelling, which is what lets
`regenerate_sage.jl` check the nine non-reproducible surfaces meaningfully.

Both verification scripts read `records/MANIFEST.tsv` and fail loudly on a hash
mismatch rather than warning: a mismatch means the upstream file changed, or your
Sage builds a different complex than the record was computed from, and either way
the affected records must not be trusted until that is understood. Sage's example
definitions and vertex labellings can change between releases, so each Sage record
pins the version string it was made under.

The canonical form the hashes are taken over is fixed in
[docs/CANONICALIZATION.md](docs/CANONICALIZATION.md); it has to be, because Sage
vertex labels can be tuples or residues and the Alexander–Whitney product depends
on the vertex order. Structure constants are quadratic in the basis, so they are
omitted above 40 basis classes (`rand2_n25` would otherwise need ~227,000
entries); such records say so and still carry every basis and representative.

## Reading the output

* **`H^d = Z^2 + Z/2`** — the group in invariant-factor form; `basis:` names the
  canonical generators.
* **the table** — row class ∪ column class, in the basis of the target degree. A
  product landing above the top degree prints `0`, which is correct: `H^d = 0`
  for `d > dim K`.
* **`ring structure`** — a presentation when `H^*` is generated by one class,
  e.g. `Q[x3]/(x3^2),  |x3| = 3` or `Z[x2]/(2*x2, x2^3),  |x2| = 2`. Otherwise it
  says to read the table. Multi-generator presentations are not implemented (see
  Limitations).
* **`checks`** — two identities that hold in *any* cohomology ring: the degree-0
  class is a unit, and `a ∪ b = (-1)^{|a||b|} b ∪ a`. Graded commutativity is
  false on cochains and only becomes true on cohomology, so this is a real
  end-to-end test rather than a tautology. `FAILED` means a bug, not an
  interesting space.

## Correctness

Homology and cohomology are computed here by two unrelated routes — a chain
complex and ranks on one side, OSCAR's `DGAlgCohRing` over a cochain complex on
the other. That makes them worth checking against each other, and against
outside authorities. This section records what is checked, what the corpus
currently reports, and what is *not* guaranteed.

### The cross-check: H_* against H^*, over ten rings

`scripts/verify_homology.jl --cross` computes both sides for every space and
compares them. What is compared depends on the ring:

* **over a field** — `dim H_d == dim H^d`;
* **over `ZZ`** — universal coefficients: the free rank of `H^d` matches that of
  `H_d`, and the **torsion** of `H^d` matches that of `H_(d-1)`. The degree
  shift is exactly where the two constructions differ, so this is the only check
  that exercises torsion across both code paths.

The ring grid spans characteristic 0, prime fields, and prime-power fields at
several characteristics:

| | rings |
|---|---|
| characteristic 0 | `ZZ`, `QQ` |
| prime order | `GF(2)`, `GF(3)`, `GF(5)`, `GF(7)` |
| prime power order | `GF(4) = F_2^2`, `GF(8) = F_2^3`, `GF(9) = F_3^2`, `GF(25) = F_5^2` |

**Result over the whole corpus: 197 spaces × 10 rings = 1970 comparisons, zero
disagreements.**

### The other checks

| check | scope | result |
|---|---|---|
| OSCAR/Polymake integral homology | every space | 197 / 197 agree |
| Independent integral homology, re-derived here (`--deep`) | 195 of 197 (two too large) | 195 / 195 agree |
| The `H_*` line Lutz's files publish in their own headers | the single-complex files | 12 / 13 agree — see below |
| Cup product laws: unit, graded commutativity (`check_ring`) | every ring record | all pass |
| Euler characteristic against the f-vector | every space | all pass |
| Test suite | offline / online | 243 / 279 pass |

### What is *not* independent

**Over `ZZ`, agreement with `Oscar.homology` is definitional, not evidence.**
Integral Smith normal form does not scale — `snf` of `RP^5`'s third boundary
matrix (2277 × 1174) did not finish in four minutes — so the `ZZ` path delegates
to Polymake. Comparing the two therefore compares Polymake with itself. It still
catches packing mistakes, and `--deep` re-derives integral homology here
independently for complexes small enough to afford it, but the honest
independent checks over `ZZ` are the published headers and the universal-
coefficients cross-check above.

### One source disagrees with itself

`SU2_SO3` is reported as differing from its published header. Its file states
`H_* = (Z,0,Z,Z,0,Z)`, the homology of `S^2 x S^3`, but reproduces the f-vector
`(13,78,286,533,468,156)` exactly — and Polymake, the chain complex here, and
the cup product machinery all give `(Z,0,Z/2,0,0,Z)`, the Wu manifold
`SU(3)/SO(3)`. Three independent computations side against the header, so the
catalogue lists it as the Wu manifold and the test suite pins both results.

### Bugs these checks caught

Worth recording, because each was found by a check rather than by reading:

* **`NotIConnected(5,2)` came out as `Z^7` instead of `Z^6`.** The first
  homology implementation presented the *unsimplified* subquotient, and OSCAR
  returned 19 relation rows where the image of the sixth boundary map has rank
  20 — one relation silently dropped. The f-vector forces Euler characteristic
  −5, which 7 violates, and the complex is known to be a wedge of `(5−2)! = 6`
  five-spheres. Switching to ranks, done for speed, removed the bug; the
  cohomology side was never affected because it has always presented the
  simplified complex.
* **`scripts/run_tables.jl` failed on every space.**
  `simplicial_cohomology_ring(::SpaceEntry, R)` called `e.build()` on a struct
  whose field is `recipe`. It shipped broken and is now covered by a test.
* **`scripts/regenerate_sage.jl` claimed more than it did.** Its output said
  "f-vector and homology match" while comparing only the f-vector. It now reads
  `MANIFEST.tsv`, which carries `f_vector` and `integral_homology` columns, so
  the claim is true.

## Time budget

Every computation takes a `time_limit`, 300 seconds by default:

```julia
simplicial_cohomology_ring("HP^2", catalogue_space("HP^2"), GF(7); time_limit = 300)
```

```bash
julia scripts/run_tables.jl --time-limit 300   # overruns are skipped and reported
```

**This is a cooperative budget.** It is tested between degrees while the graded
pieces are built and between rows while the table is filled, so it stops at the
next boundary rather than pre-empting. A single long call into OSCAR — and from
there into Singular or Flint, which Julia cannot interrupt — will overrun it:
asking for `S^2 x Poincare sphere` with a 5-second limit raises at **135
seconds**, at the first check after `H^0` finished.

For a limit that actually binds,
[`scripts/run_isolated.jl`](scripts/run_isolated.jl) gives each space its own
process and kills it on the clock:

```bash
julia scripts/run_isolated.jl --time-limit 300 --out tables.txt
```

The cost is one Julia + OSCAR startup per space, about 35 seconds.

A second guard: `print_report(X; max_table = 40)` skips the table when the total
number of basis classes exceeds `max_table`, since both the table and the checks
are quadratic in it. `PG128` would need 6.5 million products.

Facet count is a poor predictor of cost; what hurts is the **size of the
cohomology**. `PG128` is a 2-complex on 127 vertices, which looks cheap, but
`H^1` has rank 2541 and it does not finish.

Six entries are marked `heavy` because they were measured not to finish:
`PG64`, `PG128`, `AG_5_3`, `Hom_C5_K5`, `Hom_C6_compl_K5` and
`Hom_n9_655_compl_K4`. `catalogue()` includes them, `catalogue(; heavy = false)`
does not, and the drivers skip them unless you pass `--all` or name one with
`--only`. They stay in the catalogue because they are legitimate spaces, not
because they will finish. Everything else is fast: the slowest of the other 197
are `S^2 x Poincare sphere` (~210s), `HP^2` (dimension 8, 32s) and `CP^3` (12s).

## What OSCAR provides, and what this repo adds

The relevant OSCAR code is in `experimental/DoubleAndHyperComplexes/src/`.

In one line: OSCAR supplies the *cochain* complex and the cup product on it, but
no coordinates; it supplies integral homology through Polymake, but no
homology over any other ring. This package adds the coordinates, a *chain*
complex for the field cases, a catalogue, records and verification.

**`Objects/simplicial_complex.jl`** builds `SimplicialCochainComplex(R, K)` as a
1-dimensional `HyperComplex` with direction `:cochain`, in degrees `0 .. dim(K)`:

* `C^i` is free of rank `f_vector(K)[i+1]`, one generator per `i`-face;
* `d^i` is the transpose of Polymake's `topaz.boundary_matrix(K, i+1)`;
* `mul_cochains(C, a, p, b, q)` is the cup product on cochains in the
  Alexander–Whitney form of Hatcher §3.2: on dual basis simplices `sigma` (a
  `p`-face) and `tau` (a `q`-face) the product is the dual of `sigma ∪ tau` when
  `max(sigma) == min(tau)` and `sigma ∪ tau` is a face, and `0` otherwise.

**`cohomology_ring.jl`** wraps that in `DGAlgCohRing`, whose elements are
cohomology classes: `graded_part(A, i)` is `homology(C, i)[1]`; multiplication
distributes over homogeneous parts and applies `mul_cochains` to representatives;
`small_generating_set(A, d)` pulls generators back from a cached `simplify(C)`.

**Homology** has no OSCAR counterpart to wrap. `Oscar.homology(K, i)` on a
`SimplicialComplex` is Polymake and integral only, so
[`src/chain_complex.jl`](src/chain_complex.jl) mirrors OSCAR's cochain file with
three changes — direction `:chain`, the boundary matrix untransposed, and maps
for `1 <= i <= dim(K)` — and [`src/homology_tables.jl`](src/homology_tables.jl)
reads the groups off it. Should this ever be upstreamed, that is the whole diff.

What OSCAR does **not** give is **coordinates**: a product comes back as a
cohomology class, not a combination of named generators, so no multiplication
table falls out directly. That is what
[`src/ring_tables.jl`](src/ring_tables.jl) adds. Per degree it

1. takes `small_generating_set(A, d)` as generators `g_1..g_k` of `H^d`;
2. reads the relation matrix between them off `presentation`;
3. puts that matrix in Smith normal form `T*Rel*V = S`, turning `H^d` into
   `(+)_j R/(S_jj)` — separating free summands from torsion (so `RP^4` prints
   `H^2 = Z/2` rather than "one generator") and dropping collapsed generators;
4. names the surviving basis and expresses every product in it.

[`src/canonical.jl`](src/canonical.jl) holds the parts both sides share: the
Smith normal form, the basis labels, and the wall-clock budget.

## Known limitations

**`CP^n` for n ≥ 4 is not available.** No explicit triangulation is known that
anything can compute with. Arnoux–Marin gives a lower bound of `(n+1)^2`
vertices, with equality only for `n ≤ 2`. The one published construction for
`n ≥ 4` (Datta–Spreer, [arXiv:2401.09891](https://arxiv.org/abs/2401.09891))
takes the first derived subdivision of a simplicial cell complex with `(2n)!/n!`
facets — for `n = 4` that is `1680 * 9! = 609,638,400` facets in dimension 8. An
earlier announced family (Sarkar) was withdrawn from arXiv.

**Ring presentations only cover the singly-generated case.** `identify_ring`
returns e.g. `Q[x3]/(x3^2)` when `H^*` is generated by one class, and `nothing`
otherwise — so the torus, K3, the Wu manifold and most 3-manifolds here print a
table but no presentation. A general presentation (indecomposables as
generators, then the kernel of the free graded-commutative algebra, searched up
to degree `top + max_generator_degree`) is a well-defined extension over field
coefficients; it is not implemented.

**One Manifold Page file contradicts itself.** `SU2_SO3` publishes
`f=(13,78,286,533,468,156)` and `H_*=(Z,0,Z,Z,0,Z)` — the homology of `S^2 x
S^3`. Its facet list reproduces the f-vector exactly, so the complex is the
intended one, but OSCAR's `homology(K, i)` (Polymake, a code path entirely
separate from this repo) and the cup product machinery here **both** give
`H_* = (Z, 0, Z/2, 0, 0, Z)`. That is the Wu manifold `SU(3)/SO(3)`, whose
vertex-minimal triangulation has 13 vertices — and `SO(3)` is not a subgroup of
`SU(2)` in the first place, so the header reads as a slip for `SU(3)/SO(3)` with
an `H_*` line copied from elsewhere. The catalogue lists it as the Wu manifold
and the test suite pins both computations.

**An OSCAR bug affects 0-dimensional complexes.** `Oscar.simplify` on a
hypercomplex whose only non-trivial term has neither an incoming nor an outgoing
map never populates `maps_to_original`, then throws

```
KeyError: key 0 not found
  Oscar.SimplifiedChainFactory ... simplified_complexes.jl:325
```

For simplicial cochain complexes that bites exactly when `dim(K) == 0` — the
point — taking `small_generating_set`, `integral` and `set_volume_form!` with it.
`_raw_generators` in `src/ring_tables.jl` routes around it by reading the
homology of the unsimplified complex, which is already minimal there
(`H^0 = C^0` when there are no differentials).
